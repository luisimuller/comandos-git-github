Comandos Git y GitHub útiles

Guía personal de comandos de Git y GitHub, con una explicación breve de qué hace cada uno y cuándo usarlo.

1. Configuración inicial de Git

Antes de empezar a trabajar con Git, es necesario configurar algunos datos que permitan identificar quién realiza los cambios en un proyecto. Esta configuración se hace una sola vez por computadora, ya que Git la guarda y la utiliza en todos los repositorios en los que trabajemos.

Configurar nombre y correo electrónico

Cada vez que guardamos un conjunto de cambios mediante un commit, Git registra quién lo realizó. Para eso, debemos configurar nuestro nombre y correo electrónico: 

git config --global user.name "Tu Nombre"
git config --global user.email "tu-email@ejemplo.com"

El nombre y el correo que configuremos quedarán asociados a nuestros commits, permitiendo identificar al autor de cada modificación.

Establecer main como rama principal

Cuando creamos un repositorio nuevo, Git necesita definir cuál será su rama inicial. Con el siguiente comando podemos establecer main como nombre predeterminado, utilizando el mismo criterio que GitHub: 

git config --global init.defaultBranch main

De esta manera, cada vez que inicialicemos un repositorio nuevo, su rama principal se llamará main automáticamente.

Verificar la configuración

Si queremos comprobar que nuestro nombre quedó configurado correctamente, podemos ejecutar: 

git config --global user.name

Git nos devolverá el nombre que guardamos. De la misma manera, podemos verificar nuestro correo electrónico: 

git config --global user.email

Estos comandos nos permiten consultar la configuración sin modificarla.

2. Buenas prácticas: trabajo individual

Cuando trabajamos solos en un proyecto, podemos gestionar nuestros cambios directamente sobre la rama principal (main), sin necesidad de coordinarlos con otros desarrolladores. Sin embargo, es importante mantener un orden de trabajo para conservar un historial claro de los cambios y evitar perder información.

Flujo de trabajo diario

Cuando trabajamos en un proyecto, es habitual realizar modificaciones en los archivos y guardar esos cambios utilizando Git. El proceso tiene cuatro pasos: revisar qué cambió, seleccionar los archivos, crear un commit y subir los cambios a GitHub. 

git status
git add archivo
git commit -m "tipo: mensaje"
git push
  • git status: muestra el estado actual del repositorio. Permite identificar qué archivos fueron modificados, cuáles son nuevos y cuáles están preparados para el próximo commit.
  • git add: selecciona los archivos o cambios que queremos incluir en el próximo commit.
  • git commit: registra los cambios preparados en el historial del repositorio. El mensaje permite identificar qué se modificó.
  • git push: envía los commits locales al repositorio remoto, por ejemplo, GitHub.

Buenas prácticas

Aunque trabajemos solos, es importante mantener ciertas prácticas que nos ayuden a organizar el proyecto, evitar errores y conservar un historial de cambios fácil de entender.

  • Commits pequeños y frecuentes: es preferible guardar cambios concretos que tengan un único propósito, en lugar de acumular muchas modificaciones en un solo commit.
  • Mensajes claros: escribir mensajes que expliquen qué se modificó. Podemos utilizar Conventional Commits, por ejemplo: feat: agrega formulario de registro o fix: corrige validación de email.
  • Hacer push regularmente: subir los cambios a GitHub con frecuencia permite tener una copia remota del trabajo y acceder a él desde otros dispositivos.
  • Actualizar antes de empezar: si trabajamos desde más de una computadora, conviene ejecutar git pull antes de comenzar para incorporar los cambios que hayamos subido desde otro equipo.
  • Usar ramas para experimentar: aunque trabajemos solos, podemos crear una rama para probar funcionalidades o realizar modificaciones que todavía no estamos seguros de conservar. Así podemos experimentar sin afectar directamente a main.

3. Buenas prácticas: trabajo en equipo

Cuando varias personas trabajan en un mismo proyecto, es necesario organizar cómo se realizan y se incorporan los cambios para evitar sobrescribir el trabajo de otros desarrolladores o generar conflictos. Para eso, Git permite trabajar con ramas (branches), de manera que cada integrante pueda desarrollar sus tareas de forma independiente sin modificar directamente la rama principal.

Flujo de trabajo con ramas (GitHub Flow)

GitHub Flow es una metodología de trabajo que permite organizar el desarrollo de un proyecto utilizando ramas. Cada desarrollador trabaja en una rama independiente para realizar una tarea y, cuando termina, propone incorporar sus cambios a la rama principal mediante un Pull Request (PR).

De esta manera, los cambios pueden revisarse y aprobarse antes de integrarse a main, ayudando a mantener el proyecto organizado y funcionando correctamente.

1. Actualizar la rama principal

Antes de comenzar una nueva tarea, debemos posicionarnos en la rama principal (main) y descargar los últimos cambios del repositorio remoto. Esto permite comenzar a trabajar sobre una versión actualizada del proyecto. 

git switch main
git pull

git switch main: cambia a la rama principal del proyecto.

git pull: descarga e incorpora los cambios más recientes del repositorio remoto a nuestra rama local.

2. Crear una rama para nuestra tarea

Una vez que tenemos main actualizado, creamos una nueva rama para trabajar en nuestra tarea. Es recomendable utilizar un nombre descriptivo que indique qué funcionalidad vamos a desarrollar o qué problema vamos a corregir. 

git switch -c feat/nombre-de-la-tarea

Este comando crea una nueva rama y nos posiciona automáticamente en ella. A partir de ese momento, todos los cambios y commits que realicemos quedarán asociados a esa rama.

3. Trabajar y guardar los cambios

Una vez creada la rama, podemos trabajar en nuestra tarea sin modificar directamente la rama principal. Cuando tengamos cambios para guardar, primero los preparamos y luego creamos un commit. 

git status
git add .
git commit -m "feat: agregar formulario de registro"
  • git status: muestra qué archivos fueron modificados.
  • git add .: prepara todos los cambios para incluirlos en el próximo commit.
  • git commit: guarda los cambios preparados en el historial de Git, con un mensaje que describe qué hicimos.

4. Subir nuestra rama al repositorio remoto

Una vez que guardamos nuestros cambios mediante uno o varios commits, debemos subir nuestra rama a GitHub. De esta manera, los demás integrantes del equipo podrán acceder a nuestro trabajo. 

git push -u origin feat/nombre-de-la-tarea
  • git push: envía los commits de nuestra rama local al repositorio remoto.
  • origin: es el nombre habitual que Git asigna al repositorio remoto.
  • -u: establece una relación entre nuestra rama local y la rama remota. Así, en los próximos envíos podremos utilizar simplemente git push.

5. Crear un Pull Request (PR)

Después de subir nuestra rama a GitHub, debemos crear un Pull Request. Este mecanismo permite proponer que los cambios realizados en nuestra rama se incorporen a otra rama, generalmente main.

Para crearlo, ingresamos al repositorio en GitHub y seleccionamos la opción Compare & pull request. Allí debemos verificar que la rama de destino sea main y que la rama de origen sea la que contiene nuestros cambios.

En el Pull Request podemos agregar un título y una descripción explicando qué modificamos y por qué. Luego, lo creamos para que otros integrantes del equipo puedan revisar el código.

  • Revisión de código (Code Review): otros desarrolladores pueden revisar los cambios, dejar comentarios y solicitar modificaciones antes de integrarlos.
  • Aprobación: si los cambios cumplen con los criterios del equipo, pueden aprobarse para continuar con la integración.

6. Aprobar y fusionar el Pull Request (Merge)

Una vez revisados los cambios, si el equipo considera que están correctos, el Pull Request puede aprobarse y fusionarse con la rama principal (main).

Para hacerlo, ingresamos al Pull Request en GitHub y seleccionamos la opción Merge pull request. Luego confirmamos la operación.

El proceso de merge integra los cambios de nuestra rama con la rama de destino. De esta manera, las modificaciones pasan a formar parte del proyecto principal.

  • Merge: combina los cambios de una rama con otra.
  • Conflictos: pueden aparecer cuando dos desarrolladores modifican partes incompatibles de un mismo archivo. En ese caso, es necesario resolverlos antes de completar la integración.

7. Actualizar main y eliminar la rama de trabajo

Una vez que el Pull Request fue fusionado, podemos volver a nuestra rama principal y actualizarla para incorporar los últimos cambios. Después, podemos eliminar la rama que utilizamos para desarrollar nuestra tarea, ya que dejó de ser necesaria. 

git switch main
git pull
git branch -d feat/nombre-de-la-tarea
  • git switch main: vuelve a la rama principal.
  • git pull: actualiza nuestra rama local con los últimos cambios del repositorio remoto.
  • git branch -d: elimina la rama local que ya fue fusionada.

También podemos eliminar la rama remota desde GitHub, una vez completado el Pull Request, si ya no necesitamos conservarla.

Buenas prácticas para trabajar en equipo

Además de seguir un flujo de trabajo ordenado, es importante establecer ciertos hábitos que faciliten la colaboración entre desarrolladores y ayuden a evitar problemas en el proyecto.

  • Una tarea, una rama: crear una rama independiente para cada funcionalidad o corrección.
  • Actualizar antes de trabajar: incorporar los últimos cambios de main antes de comenzar una nueva tarea.
  • Evitar trabajar directamente sobre main: utilizar ramas para desarrollar y probar cambios sin afectar la versión principal del proyecto.
  • Revisar el código de otros: participar en los Pull Requests, aportar comentarios y detectar posibles errores.
  • Resolver conflictos: comunicarse con el equipo cuando dos cambios entren en conflicto y acordar cómo integrarlos.
  • Usar mensajes descriptivos: escribir commits que permitan entender rápidamente qué se modificó.

Conflictos en Git (Merge Conflicts)

Un conflicto ocurre cuando Git no puede combinar automáticamente dos conjuntos de cambios. Esto puede suceder, por ejemplo, cuando dos desarrolladores modifican las mismas líneas de un archivo de manera diferente.

Cuando aparece un conflicto, Git necesita que indiquemos qué cambios queremos conservar antes de completar la integración de las ramas.

¿Cómo identificar un conflicto?

Al intentar fusionar dos ramas, Git informa que existen conflictos y deja marcadas las partes del archivo que necesitan resolverse. Podemos consultar qué archivos están afectados utilizando: 

git status

Dentro del archivo encontraremos marcas similares a estas:

<<<<<<< HEAD
Cambios de nuestra rama
=======
Cambios de la otra rama
>>>>>>> otra-rama
  • <<<<<<< HEAD: indica el comienzo de los cambios de la rama actual.
  • =======: separa las dos versiones del contenido.
  • >>>>>>> otra-rama: indica el final de los cambios de la otra rama.

¿Cómo resolverlo?

Debemos abrir el archivo afectado, revisar ambas versiones y decidir qué contenido conservar. Podemos elegir una de ellas o combinar partes de ambas. Después, eliminamos las marcas del conflicto y guardamos el archivo.

Una vez resuelto, indicamos a Git que el archivo está listo y completamos la operación de merge: 

git add archivo
git status
git commit

En algunos casos, Git completa la integración automáticamente. Si el merge quedó pendiente por un conflicto, después de resolverlo y preparar los archivos con git add, podemos finalizarlo utilizando git commit.

  • git add: marca el archivo como resuelto.
  • git status: permite verificar que ya no quedan conflictos pendientes.
  • git commit: completa la integración de los cambios cuando el merge requiere un commit.

Es importante revisar el resultado y probar que el proyecto siga funcionando correctamente antes de continuar.

Otros comandos útiles de Git

Además de los comandos utilizados en el flujo de trabajo, existen otras herramientas que nos permiten consultar el historial, comparar modificaciones y administrar las ramas del proyecto.

Consultar y administrar ramas

git branch
git branch -a
git switch nombre-de-la-rama
  • git branch: muestra las ramas locales del repositorio y marca con un asterisco (*) la rama en la que estamos trabajando.
  • git branch -a: muestra las ramas locales y las ramas remotas.
  • git switch: permite cambiar de una rama a otra.

Consultar el historial de cambios

git log --oneline

Muestra el historial de commits en un formato resumido, incluyendo el identificador y el mensaje de cada commit.

Comparar modificaciones

git diff

Permite visualizar las diferencias entre los cambios realizados en los archivos y los cambios que ya fueron preparados para el próximo commit. Por defecto, muestra los cambios que todavía no fueron preparados con git add.
